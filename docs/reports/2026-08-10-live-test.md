# Live gate on the merged L0–L2 capabilities — 2026-08-10

All ten default-flags capabilities run clean against real LinkedIn, and every stored row is
verified by direct Supabase query rather than by the receipt. **Four defects were found and
fixed**, three of which produced clean exit-0 receipts while losing or corrupting data — the
failure class that matters, because nothing in the run says anything is wrong. The worst:
`profile.get` stored a lead with no employer, and had done so on every profile run since
2026-08-08. No challenge, no rate limit, no auth failure, no leftover tab, no wedged lease
across the whole session. 53 page loads of the 400/day and 60/hour ceilings; 2 distinct profiles.

## [BUG, fixed] `profile.get` stored a lead with no employer — and always had

**Impact.** `current_company_urn: null` and zero experience rows for a profile headlined "CEO at
Wispr Flow", on a clean exit 0. For a lead-qualification tool, employment is the field. Every
profile run ever recorded, back to 2026-08-08, has the same hole: no capture has ever archived
an Experience card. This was never a regression from the merge — the field never worked, and the
Task 19 M3 gate passed without it.

**Mechanism.** LinkedIn defers everything below the Activity card into seven numbered containers
(`<div id="profileCardsBelowActivityPart3tankots">`), each carrying an `onComponentAppear`
trigger at `visibilityRatio: 0` whose action is an `AsyncComponentRequest` for its own content —
read out of the initial document, not guessed. A container never scrolled into view never
fetches and stays an empty div. Experience, Education and Skills live in those containers. The
page also grows while it is read: `main#workspace` laid out at 2145px and finished at 7348px, so
a pass count fixed before the read cannot express "all of it". The randomized 3–6 passes covered
3366px and left all seven empty.

**Fix.** `readLikeAHuman` gains an opt-in `untilBottom` that reads until the page stops having
more, bounded at 20 passes. Only `profile.capture` asks for it: a feed does not end, so the feed
surfaces keep the fixed pass counts they pass explicitly, and an explicit `--scrolls` still wins
everywhere. Two silences became warnings — `PAGE_NOT_READ_TO_BOTTOM` and
`DEFERRED_SECTIONS_EMPTY`. D320.

**Verified.** `cap profile.get` on default flags now stores 6 experience rows and
`current_company_urn: urn:li:fsd_company:79835899`, with real titles and dates, confirmed by
direct query.

## [BUG, fixed] The D119 guard was inert on the activity surface

**Impact.** `profile.posts` and `profile.activity` warned `SESSION_IDENTITY_UNAVAILABLE` and
stored their rows anyway — 14 `person_posts` among them. That warning means the check that stops
a parser returning the operator's own identity for every prospect ran with an empty comparison
set. It fired four times in the first gate and nothing acted on it.

**Mechanism.** The profile surface fetches `/voyager/api/me`; `/in/<vanity>/recent-activity/all/`
never does — 38 captures in one run, not one of them `/me`. The post permalink does fetch it, so
this was never a post-surface problem.

**Fix.** The same record is server-rendered into that page as a Big Pipe island carrying
`"$type":"com.linkedin.voyager.common.Me"`, which D117 already admits as a captured body —
nothing new is requested. Urns are taken **only from inside that one labeled island**, never from
the document at large: the activity document also carries the subject's urns, and sweeping those
into the operator's set would make the guard flag every genuine subject as the operator and
suppress real data. D322.

**Verified.** Offline against the archived bodies of the profile, activity and post runs: each
resolves exactly the operator and never the subject. Live, the warning is gone from both
capabilities.

## [BUG, fixed] `job.get` overwrote a full description with a truncated one

**Impact.** Job 4434758293: `company.jobs` stored 3602 characters of description from the page's
embedded JSON; `job.get` then stored 1438, cutting the text mid-document at "What are we looking
for?". What the row held depended on which capability ran last.

**Mechanism.** `job.get` reads the description from `[data-testid="expandable-text-box"]`, which
LinkedIn renders **collapsed** — nothing clicks "see more", and the box held 940 characters of a
3602-character description. D272 promised neither writer erases what the other stored, but that
covered only whole fields; a truncation is the same erasure done partially and passed straight
through.

**Fix.** `upsertJob` reads the stored description before writing one and keeps the longer text,
failing open if the read fails. The batch writer now drops explicit nulls too — `company.jobs`
omits rather than nulls today, so nothing changes in practice, but a monotonic promise only one
of two writers keeps is not one. D323.

**Verified.** `job.get` then `company.jobs` then `job.get` again on the same posting leaves
title, location, posted_at and the full 3602-character description intact.

**Not fixed, deliberately.** Expanding the description at the source means clicking "see more",
which is an interaction rather than a read, and the snapshot carries no control to anchor the
click on. Recorded in `BACKLOG.md` with what has to be settled first.

## [BUG, fixed] A readable page was thrown away three times

**Impact.** Three runs today — two profiles and a job — failed `CAPTURE_TIMEOUT` at exit 6 with
the page load already spent, while the page's own document sat archived at 1.0MB, fully
populated. Exit 6 is `RETRY_BACKOFF`, so the receipt invites a retry that spends another load on
the same outcome.

**Mechanism.** The readiness gate waited on the broad `linkedin-api` pattern alone. All three of
those readers parse the DOM snapshot rather than an API body (D123, D130, D305, D313), so they
failed holding exactly what they came for. LinkedIn increasingly answers these pages
server-rendered with no Voyager call at all.

**Fix.** One shared gate (`core/tap/ready.ts`) waits for whichever arrives first — the broad API
pattern or that target's own document — and fails only when neither does. Applied to the
profile, job and activity captures. It is a readiness gate, not a safety gate: nothing new is
requested, no rule is relaxed, and the challenge gates on either side are untouched. D321.

**Verified.** `cap job.get` on a page that had failed this way twice now completes.

## [FYI] `first_seen` after `last_seen` is write latency, not clock skew

A `company_posts` row carried `first_seen 01:13:11.886` and `last_seen 01:13:09.785`. Measured
rather than argued: a throwaway upsert put the database's `now()` at `02:46:18.251127`, inside a
Node window of `02:46:18.241`–`.262`, round trip 21ms. The clocks agree; the 2.1s gap was a cold
first write being slow.

Left as is. The inversion can only appear on a row's first insert, `first_seen` is informational,
and freshness compares `last_seen` alone. Fixing it properly means a trigger, and a migration to
correct a cosmetic field is not a trade worth making. D324.

## What is still untested

- **Only one target per surface.** Parse drift shows up on variety, and one company and one
  profile cannot produce it.
- **Most flag paths.** `--no-store`, `--force-release`, `--budget`, and resume via `--run-id` were
  not exercised. `--dry-run` and the freshness cache-hit path were, incidentally: `profile.get`
  served `from_cache: true` without a page load.
- **Every non-zero exit but 6.** No challenge, rate-limit, auth-dead or budget-exhausted path was
  reached, which is the good outcome and also means those paths are unproven live.

## Needs your decision

Nothing blocking. Two things worth your call when you have time:

1. **Freshness serves an incomplete row.** `profile.get` returned `from_cache: true` for a person
   whose stored `experience_rows` was 0. The cache is honest about age and says nothing about
   completeness. Worth deciding whether a row missing its employment should count as fresh.
2. **Job descriptions stay truncated when nothing else has listed the posting.** The store guard
   stops a truncation destroying a full text, but a posting seen only through `job.get` still
   stores about a quarter of its description. The backlog entry offers a cheaper interim: report
   it as partial rather than as the whole.
